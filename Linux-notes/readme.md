SDLC - The Software Development Life Cycle (SDLC) is a systematic `process` software engineers and developers use to `design, develop, and test high-quality software`. The SDLC aims to produce software that meets or exceeds customer expectations, reaches completion within times and cost estimates, and is efficient and maintainable. The life cycle defines a methodology for improving the quality of software and the overall development process


`Planning`: This is the initial stage in the SDLC, where the project's scope is determined, and a high-level plan for the project is established. This phase involves determining the resources, team roles, and project goals, and identifying potential risks. The planning stage sets the stage for the rest of the project. This is a critical stage because it can either make or break the process. 

`Requirement Analysis`: After planning, the next step is to define and document the product requirements and get them approved by the customer or the market analysts. This is done through detailed communication with the project stakeholders.


`Design`: The requirement specifications from the first phase are studied in this phase, and the system design is prepared. This system design helps in specifying hardware and system requirements and defining the overall system architecture.


`Implementation/Coding`: The software design is translated into source code. All the components of the software are implemented in this phase. This is typically the longest phase of the SDLC.


`Testing`: After coding (implmentation), the product is tested against the requirements to make sure that the product is solving the needs gathered during the requirements phase. During this phase, defects(issues or bugs) are reported, tracked, fixed, and retested until the product reaches the quality standards defined in the SRS.

`Deployment`: After successful testing, the system is deployed (delivered ) to the customer for their use. Sometimes the software is released in stages as per the business strategy of that system.


`Maintenance`: Once the system is deployed, and customers start using the developed system, the problems come up and need to be solved from time to time. This process where the care is taken for the developed product is known as maintenance.



`Methods or Steps ( Methodology used in Software development )`


1. `Waterfall Methodology ( Traditional approach )` : 

This is the classic SDLC model, with a linear and sequential approach, where each phase must be completed before the next phase can begin. It's straightforward but can be inflexible as it doesn't easily accommodate changes during the development process.


`Analogy of the Waterfall Model:`


Imagine building a house (the software) using the Waterfall model (the methodology). First, you sit down with the architect to detail every nook and cranny of your dream home. This is the requirements phase, where you decide on everything you want and need before any construction begins.

Next, you move on to the design phase, where those requirements are turned into blueprints. Just like in Waterfall, once you've finalized these plans, you can't decide you want a bigger kitchen or an extra bathroom; the design is set.

Then, the construction phase begins. This is like the implementation phase in software development. Workers (developers) follow the blueprints (design documents) to build the house (software). They can't change the plan or go back to add a window because they think it'll look nice; they must follow the plan.

After construction, an inspector (tester) comes in to check if everything is built correctly and to code. If something's wrong, it's a big deal to fix it because everything else was built on the assumption that the previous work was done right.

Finally, you move in (deployment), but if you find problems or want changes, it's costly and time-consuming because the house is already built. You might even need to start over for significant changes.


What are some of the disadvantages of the Waterfall Methodology ? 

+ `inflexibility to change `: Once a phase is completed, it's difficult to go back and change something. If the requirements were misunderstood from the start, it could lead to a useless product or expensive rework.

+ `Late Testing`: Testing occurs late in the process, which means any issues found are more expensive and time-consuming to fix. This is because they may require going back several stages to correct.

+ `Poor Adaptability`: If the client's needs change during development, the Waterfall model struggles to accommodate these changes without significant rework or starting over.

+ `Assumption of Perfect Understanding`: The Waterfall model assumes that every requirement can be identified before any design or coding occurs. This is often unrealistic, as clients may not know exactly what they need at the outset or may change their minds as they see the project evolve.

+ `Delayed Delivery`: The product is only tested and delivered at the end of the development cycle. This means clients have to wait longer to see any working software, and it might be outdated or irrelevant by the time it's delivered.

`How did DevOps Came into Existence ?`

DevOps came about because development and operations teams traditionally worked separately, which caused slow releases, communication problems, and frequent production failures.

What is Operations team ? The Operations team (Ops) is responsible for keeping an organization’s applications, servers, networks, and cloud infrastructure available, secure, reliable, and performing properly.


`The old way`

+ Developers wrote the application and passed it to Operations.
+ Operations deployed and supported it.
+ Developers wanted to release changes quickly.
+ Operations wanted stability and fewer changes.
+ Testing and deployment were mostly manual.
+ When something failed, the teams often blamed each other.

This separation became known as the “wall of confusion.”

`How DevOps emerged`

In the early 2000s, Agile helped development teams build software faster through short iterations. However, Operations was often excluded, so deployment remained slow and difficult.
In 2007–2008, IT consultant Patrick Debois became interested in `improving collaboration between development and operations`.


In 2009, two important events helped establish the movement:

+ John Allspaw and Paul Hammond presented “10+ Deploys per Day: Dev and Ops Cooperation at Flickr.”
+ Patrick Debois organized the first DevOpsDays conference in Belgium.
The term DevOps came from Development + Operations and grew out of the DevOpsDays community.

**LINUX FILE & DIRECTORY PERMISSION MANAGEMENT ***

Linux OS - Support multi users 

In linux we have files and directories and each of these files or directories have permissions
the permissions authorized who can read , make changes to the file or execute the file 

On linux there are different types of permissions you can give a user to manage files or directories 

R = Read permission 
W = Write permisison 
X = Execute permission 
- = No Permission 


Who can we assign permissions to ? 
In linux we can categorize users when it comes to file and directory permissions in the follow categories 

+ Users  ---3 permissions 
+ Groups ---3 permissions 
+ Others ( world ) --- 3 permission 

How can we check files or directory permission on the linux operating system 

`ls - l `

+ user who created the file or owns the file 
+ group the group that also owns the file 

`NOTE` : A Directory can have different permission and the files inside the directory will have a different permission as well 



Two ways we can change permissions on a file or directory 

`Numberic (Octal) Mode `


The numeric uses numbers to calculate and change permissions for files and directories 

Read: (r) = 4 
Write: (w) = 2 
Execute : (x) = 1 
No permission : (-) = 0 

The command we will use to change permissions is 

`chmod`

`Symbolic Mode` 

This method uses letters & symbols to change the file permissions 

Who | Operator | Permmission 

Who : = To whom you wish to set the permission ( user or group or others )
Operator : = can be + ( add a permission) , - ( remove a permission) = ( set exact permission)
Permissions : = R ( Read ) (Write) (w) , Execute (X) , (-) No permission

Unix -----linux ---> files and directories 

Files / Directories 

`/` =  Root Directory  : This is the top level directory in the Linux file system . All other directories within the system lives inside this directory and that is why its called the root 

`/bin ` (Binaries) :  This directory (folder) contains files which we call them ( Binary Files ) . These binary files are commands that the linux system understands .This is where all the command we run are saved or stored 


`/opt ` : This directory (folder) by default comes empty and is reserved to store external or additional software packages that users will download in the operating system (best practise download new softwares in the opt directories )

`/boot` : This directory (folder) contains files that helps the operating system (Linux Kernel) to start up succesfully (configuration files )

`/root` (root home directory)

This is the home directory of the root user . 

`/dev` (devices) : It contains device files that represents hardware and virtual devices (/dev/sda)--> storage represents hard drive 

`/sbin` (System Binaries) ; This directory contains administrative binaries (commands ) .These binaries (commands) helps to carryout task such as , rebooting the operating system (root user)

`/etc` : This contains system wide configuration files and it contains shell scripts used to start and initialized the system 

`/srv` (service data)  ;  It contains data(information) for services provided by the system e.g web server files by default this directory is empty . 

`/home` : The home directory stores users .Each user on the Linux server has its own directory 

`/tmp (temporary files)` : This directory is used to store temporary files created or from your application.At boot the files are deleted 

`/lib ( libraries) `: This contains shared library files ( similar files) required by the binaries /bin and /sbin

`/usr` (user program) : It contains user installed softwares and their binaries (command)and documentation. The usr (user program) directory or folder contains subdirectories  

**sr/bin*  :  It has non-essential commands binaries for all users 

**usr/lib* :  It has libraries for usr/bin and usr/sbin 

**usr/include* :   Its stores standard files used for programming c+ c++  programing 

**usr/local* :  here it contains locally installed sofware and scripts

**usr/share* :  It has architecture independent data (how the software was designed), data like documenation.

**usr/src* : This contains the source code ( usually for the linux kernel or operating system)

**usr/games*: This MMMM by default and contains software or files for games 

**usr/libexec* : This contains executable library files 

`/media ` : This directory serves as a mount point for removable media .

`/mnt` (mount) : This directory is used to temporary mount file system manually ( file storage )
by default it comes without any files system mounted.the directory is empty 


`/var` (variable) : This directory contains files that are expected to increase in size 

**/var/log* : This directory contains log files generated by your system 

**/var/spool* : The spool directory contains cron-jobs ( automated task) , mail task , printer queue 

**/var/cache*: This directory contains Cached Data from your application . 

**/var/tmp* :  These are temporary files that are stored by your system

`Commands to Manage Daemon Process ( systemd)`

`Daemon process` ? A daemon process is simply a background service that runs on a system without you directly interacting with it . Think of it as a program always working quietly in the background waiting to do its job . You dont interact with the program the way you will open apps e.g zoom , whatsapp etc . Daemon process just starts with your operating system and keeps running in the background 


`systemctl`

`Zombie process` ? is a process that is already dead but still shows up in the process table . Its called zombie process because its dead but the entry is till alive in the system 


***What is the difference between a Zombie Process and a Daemon process ?**

A zombie process is a process that has already finished execution but still has an entry in the process table because the parent hasnt collected its exit status . This means the process is not running but waiting to be clean up  while daemon process on the other is an active background service that runs continously to provide system functionaly like sshd or (nginx or apache )  - webservers
